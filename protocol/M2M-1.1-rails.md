# M2M/1.1 — Rail Adapters, Fiat Schemes, and Prepaid Credits

Normative extension to M2M/1 (PROTOCOL.md). All v1 rules apply unless this
document explicitly overrides them. M2M/1.1 is backward compatible: a v1-only
agent can ignore every field added here and still transact on the `exact`
(x402) rail.

## 1. Motivation and the rail abstraction

v1 assumed one payment rail: x402 `exact` on an EVM network. Real buyers hold
cards and bank accounts, not only USDC. v1.1 generalizes payment to a **rail
adapter** model:

- A **rail** is any settlement mechanism that can (a) present a machine-
  readable payment requirement, (b) accept a payment, and (c) produce a
  verifiable settlement reference.
- The commerce layer (quotes, orders, receipts, reputation) is rail-neutral.
- The platform never custodies funds on any rail (§7 — unchanged from v1 §8;
  this extension strengthens it).

Defined rails in v1.1:

| RailId          | Scheme          | Settlement asset | Finality class |
| --------------- | --------------- | ---------------- | -------------- |
| `x402-exact`    | `exact`         | USDC on an EVM L2| `deterministic`|
| `stripe-fiat`   | `fiat-stripe`   | card / bank debit| `reversible`   |
| `m2m-prepaid`   | `prepaid`       | platform ledger credit | `instant` (ledger-internal) |
| `m2m-escrow`    | `escrow`        | reserved (v1.2, physical goods) | `conditional` |

## 2. PaymentOption — the polymorphic accepts[] entry

An Order's `accepts[]` (v1 §4.5) becomes a discriminated union on `scheme`.
A buyer pays with ANY one option. All options in one Order MUST price the
same commercial terms (§6.4 applies per rail, comparing each option against
`order.price` in that option's own units).

### 2.1 `x402-exact` (unchanged from v1)

```json
{ "scheme": "exact", "network": "base-sepolia", "maxAmountRequired": "5000",
  "asset": "0x036C…", "payTo": "0x…", "resource": "…", "maxTimeoutSeconds": 300 }
```

### 2.2 `stripe-fiat`

```json
{ "scheme": "fiat-stripe", "network": "stripe",
  "maxAmountRequired": "500", "currency": "usd",
  "paymentUrl": "https://buy.stripe.com/…",
  "expiresAt": 1767225600, "rail": { "processor": "stripe", "statementDescriptor": "M2M" } }
```

- `maxAmountRequired` is in **fiat minor units** (cents) — the integer-money
  rule (v1 §2.3) applies to fiat too. `currency` is ISO 4217 lowercase.
- `paymentUrl` is a one-time checkout link scoped to this Order. The gateway
  creates it at order time and invalidates it when the Order leaves ACCEPTED.
- Settlement confirmation arrives via processor webhook; the gateway maps the
  processor's charge id onto the Receipt (`settlementRef`, §4).

### 2.3 `m2m-prepaid`

```json
{ "scheme": "prepaid", "network": "m2m-ledger", "maxAmountRequired": "5000",
  "asset": "USD6", "account": "0xBuyerWallet…" }
```

Debits the buyer's prepaid ledger balance (§5). `asset: "USD6"` is the
ledger's synthetic unit: 6-decimal USD-denominated integer credit,
1:1 backed by settled top-ups. It is NOT a token, NOT transferable between
accounts, and NOT redeemable except as service spend — this is what keeps it
outside custody/transmission territory (§7).

### 2.4 `m2m-escrow` (reserved)

Defined in v1.2 with physical-goods fulfillment states. Listed here so
implementations reserve the scheme name.

## 3. Finality classes and receipts

Rails differ in reversibility; v1.1 makes that explicit rather than hiding it.

| Finality class   | Meaning | Rails |
| ---------------- | ------- | ----- |
| `instant`        | Ledger-internal, final on write | prepaid |
| `deterministic`  | Final when the chain confirms; no reversal path | x402-exact |
| `reversible`     | Final only after the dispute window closes | stripe-fiat (card chargebacks, typically ≤120 days) |
| `conditional`    | Final on delivery attestation | escrow (v1.2) |

Receipt (v1 §4.6) gains three optional fields; v1 consumers ignore them:

- `settlementRef`: rail-specific proof — `txHash` for x402, processor charge
  id for stripe-fiat, ledger entry id for prepaid. Exactly one is present and
  it determines which legacy field it maps to (`txHash` remains for x402).
- `finalityClass`: one of the four above.
- `finalAt`: unix seconds after which the receipt is irreversible. For
  `instant`/`deterministic` it equals `settledAt`. For `reversible` it is
  `settledAt + disputeWindowSeconds`. Buyers' agents SHOULD treat receipts as
  provisional until `finalAt`; sellers MUST NOT treat reversible-rail revenue
  as payout-eligible before `finalAt`.

## 4. Refunds (v1 reserved REFUNDED; v1.1 defines it)

- `x402-exact`: refunds are explicit outbound transfers initiated by the
  seller; the Order transitions SETTLED → REFUNDED with the refund's
  settlementRef recorded. There is no forced reversal.
- `stripe-fiat`: chargebacks arrive asynchronously from the processor. The
  gateway MUST handle the dispute webhook, transition the Order to
  `DISPUTED` immediately and to `REFUNDED` if the dispute resolves against
  the seller, and record it in the seller's reputation (chargebacks are a
  strong negative Bayesian signal — see the reputation model).
- `m2m-prepaid`: refunds are ledger credit-backs; instant and free.

## 5. The prepaid ledger

### 5.1 Accounts and conservation

The prepaid subsystem is a **double-entry ledger**, not a balance field.
Every movement is a LedgerEntry:

```
LedgerEntry {
  entryId, accountId, direction: "debit" | "credit",
  amount: BaseUnitAmount,        # USD6 integer
  refType: "topup" | "spend" | "refund" | "fee" | "payout",
  refId,                          # orderId / topup session id / payout id
  createdAt: unix seconds,
  idempotencyKey: string          # unique; retries never double-post
}
```

The ledger-wide conservation invariant, verifiable by replay at any time:

```
Σ credits − Σ debits = Σ current balances
Σ topups settled on rail R = Σ ledger credits of refType "topup" from rail R
```

Any drift means a bug or fraud; a daily reconciliation job MUST verify both
equations and halt crediting on mismatch (fail closed).

### 5.2 Top-up flow

1. `POST /v1/accounts/topup` with `{ rail: "stripe-fiat" | "x402-exact", amount }`.
2. Gateway returns a payment requirement on the chosen rail.
3. On rail settlement (webhook / facilitator), the ledger posts one credit
   entry, idempotent on the rail's settlement id. Retried webhooks post once.
4. Balance = sum of entries; there is no mutable balance row to race.

### 5.3 Spend flow

When an Order is paid via the `prepaid` option, the gateway MUST, in one
atomic transaction: verify `balance ≥ order.price`, post the debit entry, and
transition the Order to SETTLED with `finalityClass: "instant"`. If balance
is insufficient, the Order is rejected with `INSUFFICIENT_BALANCE`
(error-code addition, §8) and the buyer is offered a top-up requirement.

### 5.4 Why this is the netting embryo

Prepaid collapses N per-call settlements into 1 top-up. The P2 netting ledger
generalizes the same conservation machinery across counterparties. Build this
correctly and P2 is an extension, not a rewrite.

## 6. Trust tiers in the registry

Sellers carry a `trustTier` in their registry record:

| Tier            | Requirements | Capabilities |
| --------------- | ------------ | ------------ |
| `crypto_native` | valid EVM payout address | x402 rail only |
| `verified_fiat` | processor KYC/KYB passed (Stripe Connect or equivalent) | all rails, fiat payout, `verified` badge in /v1/services |
| `enterprise`    | verified_fiat + MSA + SLA | compliance exports, dedicated support, custom fee schedule |

ServiceDescriptor gains optional `trustTier`; buyers' agents MAY filter
discovery by tier. The tier is platform-asserted metadata, not a payment
field — it MUST NOT appear in `accepts[]` options.

## 7. The custody boundary (strengthened)

1. Platform ledger credits are spendable only on platform services; they are
   never transferable between users and never redeemable for cash by users.
2. All fiat funds flow buyer → processor → seller. All crypto funds flow
   buyer → chain → seller. Platform fee collection is via invoice (or a
   splitter contract, H4) — never via platform-held balances.
3. The platform's ledger is a record of *claims on services*, not a store of
   *value*. Counsel confirms this framing in Phase 2; if counsel disagrees,
   prepaid ships with processor-held balances instead.

## 8. Additions to the v1 error taxonomy

| Code                    | HTTP | retryable | Meaning |
| ----------------------- | ---- | --------- | ------- |
| `INSUFFICIENT_BALANCE`  | 402  | yes (after top-up) | prepaid debit exceeds balance |
| `RAIL_UNAVAILABLE`      | 503  | yes       | chosen rail's processor/facilitator is down |
| `UNSUPPORTED_RAIL`      | 400  | no        | scheme/network this deployment doesn't serve |
| `TRUST_TIER_INSUFFICIENT` | 403 | no       | seller lacks the tier this rail requires |

## 9. HTTP binding additions

| Endpoint | Payment | Purpose |
| -------- | ------- | ------- |
| `POST /v1/accounts/topup` | rail-specific | fund a prepaid balance |
| `GET /v1/accounts/{id}`   | free, owner-scoped | balance + recent entries |
| `GET /v1/accounts/{id}/receipts` | free, owner-scoped | receipt history |
| `POST /v1/webhooks/{rail}` | rail-authenticated | processor settlement callbacks (signature-verified per rail) |

Webhook authenticity is mandatory: stripe signatures, facilitator attestations,
or HMAC with per-rail secrets. An unverified webhook MUST be dropped.

## 10. Implementation order

1. Schemas + `@m2m/protocol` types (this document's companion).
2. Prepaid ledger on D1 with the conservation reconciliation job.
3. `stripe-fiat` top-up in processor **test mode**; prepaid spend on existing
   services.
4. Order-level multi-rail `accepts[]` (fiat option beside x402).
5. Trust tiers + Stripe Connect seller onboarding (H3).
6. Escrow reserved for v1.2 (physical goods, H5).
