# M2M Commerce Protocol — v1 (M2M/1)

Normative specification for the commerce layer of m2m-exchange. The key words
MUST, MUST NOT, SHOULD, and MAY are to be interpreted as in RFC 2119.

Extensions: **M2M/1.1** (rail adapters, fiat schemes, prepaid credits, trust
tiers) lives in [M2M-1.1-rails.md](./M2M-1.1-rails.md) with schemas under
`schemas/v1.1/`. v1.1 is additive; everything below remains valid.

## 1. Scope and layering

M2M/1 defines how autonomous buyer and seller agents discover services,
obtain priced quotes, place orders, and receive settlement receipts. It does
**not** define how money moves — payment is delegated entirely to x402.

```
  L2  M2M/1 commerce protocol  (this document)  — discovery, quotes, orders, receipts
  L1  x402 v1 payment rail     (Coinbase x402)  — 402 challenges, EIP-3009 USDC, receipts
  L0  HTTP + JSON                               — transport, TLS required outside localhost
```

Rules that keep the layering clean:

- M2M/1 messages never duplicate payment-cryptography concerns. Amounts,
  assets, networks, and payees in M2M/1 messages are *commercial terms*; the
  x402 `accepts[]` block in an Order is the *payment instruction*. Where both
  are present they MUST agree exactly (§6.4).
- A service with static, published pricing (e.g. the P0 demo endpoints)
  MAY skip the quote/order flow entirely and be called with the plain x402
  flow. Quote/order exists for negotiated or dynamic pricing and for
  pre-payment commitment (§5).

## 2. Conventions

### 2.1 Versioning

Every M2M/1 message carries `"m2mVersion": 1`. A receiver MUST reject a
message whose `m2mVersion` it does not support with error code
`UNSUPPORTED_VERSION`. x402 payloads embedded in messages keep their own
`x402Version` field; the two versions evolve independently.

### 2.2 Identifiers

- `serviceId`, `quoteId`, `orderId`, `receiptId`: lowercase ASCII
  `[a-z0-9][a-z0-9-]{2,62}`. Ids are generated by the seller side and are
  unique per gateway deployment.
- Agent identity in v1 is the agent's EVM address (checksummed `0x…`).
  The buyer's address is authenticated at settlement time by the EIP-3009
  signature; M2M/1 adds no separate auth scheme in v1.

### 2.3 Money

- Amounts are unsigned integers encoded as **decimal strings in base units**
  of the asset (e.g. `"1000"` = $0.001 of 6-decimal USDC). Floating-point
  amounts are prohibited anywhere in the protocol.
- Every amount is meaningless without its `asset` (ERC-20 contract address)
  and `network` (x402 network string, e.g. `"base-sepolia"`). The three
  always appear together as a `MoneyAmount` object (§4.1).
- All amount arithmetic and comparison is integer arithmetic on base units.

### 2.4 Time

Timestamps are **integer Unix seconds** (matching x402's
`maxTimeoutSeconds` convention). Quote and order expiry use `expiresAt`
(unix seconds); a message is expired when `now >= expiresAt`. Senders
SHOULD allow at least 60 seconds of clock skew headroom.

### 2.5 Extensibility

Receivers MUST ignore fields they do not recognize. Senders MUST NOT place
semantics in unrecognized fields. Breaking changes require a new
`m2mVersion`.

## 3. Actors

| Actor       | Role                                                        |
| ----------- | ----------------------------------------------------------- |
| Buyer agent | Discovers services, requests quotes, pays, consumes results |
| Seller agent| Publishes services, issues quotes, fulfills paid calls      |
| Gateway     | Hosts seller APIs, enforces quotes and x402 middleware      |
| Facilitator | x402 verify/settle service (out of scope for M2M/1)         |
| Registry    | Discovery index of ServiceDescriptors (P1; gateway-hosted)  |

## 4. Core data types

### 4.1 MoneyAmount

```json
{ "amount": "1000", "asset": "0x036CbD…", "network": "base-sepolia" }
```

### 4.2 ServiceDescriptor — what a seller offers

Published in the registry and served at `GET /v1/services`. Fields:

- `m2mVersion`, `serviceId`, `name`, `description`
- `endpoint`: path relative to the gateway origin (e.g. `"/api/weather"`)
- `method`: HTTP method of the paid call
- `pricing`: one of
  - `{ "mode": "static",  "price": MoneyAmount }` — pay-per-call, no quote needed
  - `{ "mode": "quoted" }` — buyer MUST obtain a Quote before ordering
- `inputSchema` (optional): JSON Schema for the paid call's request body/params

### 4.3 QuoteRequest — buyer → seller

`POST /v1/quotes`

- `m2mVersion`, `serviceId`
- `params` (optional): request parameters the price depends on; MUST conform
  to the service's `inputSchema` if one is published

### 4.4 Quote — seller → buyer

A firm, single-use, expiring price commitment.

- `m2mVersion`, `quoteId`, `serviceId`
- `price`: MoneyAmount
- `payTo`: EVM address that will receive payment
- `expiresAt`: unix seconds
- `termsHash` (optional): keccak256 of the canonical JSON of the
  commercial terms the quote is bound to
- A quote is **single-use**: once an Order references it, it is consumed.

### 4.5 Order — buyer accepts a quote

`POST /v1/orders` with header `Idempotency-Key: <uuid>` and body:

- `m2mVersion`, `quoteId`

Response (201):

- `m2mVersion`, `orderId`, `quoteId`, `serviceId`
- `price`: MoneyAmount (copied from the quote)
- `payTo`: payee inherited from the quote
- `expiresAt`: inherited from the quote
- `accepts`: **array of x402 v1 payment requirements** for the order's
  resource URL. This is the exact object family already returned in P0 402
  bodies (`scheme`, `network`, `maxAmountRequired`, `resource`, `payTo`,
  `asset`, `maxTimeoutSeconds`, …), so existing `x402-fetch` buyers can pay
  an order with zero new code.

Retrying `POST /v1/orders` with the same `Idempotency-Key` MUST return the
original Order without consuming anything further.

### 4.6 Receipt — proof of settled commerce

Returned as JSON body alongside the paid resource response (and mirrored in
the `X-PAYMENT-RESPONSE` header by x402 at the payment layer):

- `m2mVersion`, `receiptId`, `orderId` (null for static services),
  `serviceId`
- `price`: MoneyAmount actually charged
- `payer`, `payTo`: EVM addresses
- `txHash`: on-chain settlement transaction hash
- `settledAt`: unix seconds

## 5. Transaction state machine

States of a single commercial transaction, as tracked by the gateway:

```
                 QuoteRequest            Order              paid call
     (none) ─────────────────► QUOTED ──────────► ACCEPTED ──────────► SETTLED
                                │                    │
             seller declines ──►├► REJECTED          │ settlement fails
             ttl passes ───────►├► EXPIRED     ─────►├► FAILED (retryable per x402)
                                └► CONSUMED (order placed; terminal alias of ACCEPTED)
```

Normative transition table:

| # | From     | Event                                   | To       | Emitted by |
| - | -------- | --------------------------------------- | -------- | ---------- |
| 1 | (none)   | valid QuoteRequest for `quoted` service | QUOTED   | seller     |
| 2 | (none)   | invalid/undeclinable QuoteRequest       | REJECTED | seller     |
| 3 | QUOTED   | `expiresAt` passes                      | EXPIRED  | gateway    |
| 4 | QUOTED   | valid Order + Idempotency-Key           | ACCEPTED | buyer      |
| 5 | QUOTED   | second Order on same quoteId            | —        | rejected: `QUOTE_CONSUMED` |
| 6 | ACCEPTED | x402 verify+settle succeeds             | SETTLED  | facilitator|
| 7 | ACCEPTED | settle fails (insufficient funds, etc.) | FAILED   | facilitator|
| 8 | ACCEPTED | `expiresAt` passes before payment       | EXPIRED  | gateway    |
| 9 | (none)   | paid call on `static` service           | SETTLED  | facilitator|

Invariants:

- SETTLED and REJECTED are terminal. FAILED is terminal for the Order; the
  buyer MAY create a new Order from the same quote only if it is still
  unexpired and unconsumed (an Order that FAILED does not consume the quote).
- The gateway MUST NOT fulfill a paid call for an Order in any state other
  than ACCEPTED, and MUST mark the Order SETTLED atomically with successful
  settlement. An Order is single-fulfillment: one payment, one fulfillment.
- `REFUNDED` is reserved for a future version; v1 has no refund flow.

## 6. HTTP binding

| Endpoint                       | Auth/payment        | Purpose                          |
| ------------------------------ | ------------------- | -------------------------------- |
| `GET /healthz`                 | free                | liveness (P0, unchanged)         |
| `GET /v1/services`             | free                | discovery: ServiceDescriptor[]   |
| `POST /v1/quotes`              | free                | QuoteRequest → Quote or error    |
| `POST /v1/orders`              | free, idempotent    | Order (embeds x402 `accepts[]`)  |
| `GET/POST /v1/orders/{id}/run` | x402 paywalled      | fulfill a specific ACCEPTED order|
| static service endpoints       | x402 paywalled      | P0-style direct paid calls       |

### 6.1 Discovery

`GET /v1/services` returns `{ "m2mVersion": 1, "services": [ServiceDescriptor…] }`.
Registry indexing in P1 consumes the same document.

### 6.2 Quote → order → pay

1. Buyer fetches `/v1/services`, picks a `quoted` service.
2. Buyer POSTs a QuoteRequest. Seller replies `200` + Quote, or `4xx` +
   ErrorObject (REJECTED).
3. Buyer POSTs `{ "m2mVersion": 1, "quoteId }` to `/v1/orders` with an
   `Idempotency-Key` header.
4. Buyer feeds the Order's `accepts[]` to its existing x402 client
   (`x402-fetch`) and calls the order's `resource` URL with `X-PAYMENT`.
5. Gateway checks: order exists, state ACCEPTED, not expired, payment
   amount == order price, `payTo` matches. Then settle, fulfill, and return
   the resource payload plus Receipt.

### 6.3 Static services

Services with `pricing.mode = "static"` keep the P0 flow exactly: plain
request → 402 with `accepts[]` → paid retry → 200 + receipt. No quote, no
order.

### 6.4 Agreement between layers

For any Order, the gateway MUST guarantee:

- `accepts[i].maxAmountRequired` == `order.price.amount`
- `accepts[i].asset` == `order.price.asset`
- `accepts[i].network` == `order.price.network`
- `accepts[i].payTo` == `order.payTo` (which the gateway MUST copy from the quote)

A buyer MUST verify this agreement before signing any payment, and MUST
reject the Order with `AMOUNT_MISMATCH` semantics (abandon + report) if it
does not hold.

## 7. Error object and codes

All non-2xx M2M/1 responses carry:

```json
{ "m2mVersion": 1, "error": { "code": "QUOTE_EXPIRED", "message": "…", "retryable": false } }
```

| Code                  | HTTP | retryable | Meaning                                   |
| --------------------- | ---- | --------- | ----------------------------------------- |
| `UNSUPPORTED_VERSION` | 400  | no        | `m2mVersion` not supported                |
| `INVALID_MESSAGE`     | 400  | no        | schema violation / malformed field        |
| `SERVICE_NOT_FOUND`   | 404  | no        | unknown serviceId                         |
| `QUOTE_NOT_FOUND`     | 404  | no        | unknown quoteId                           |
| `QUOTE_REJECTED`      | 422  | maybe     | seller declines to quote these params     |
| `QUOTE_EXPIRED`       | 410  | no        | quote/order past `expiresAt`              |
| `QUOTE_CONSUMED`      | 409  | no        | quote already bound to an order           |
| `ORDER_NOT_FOUND`     | 404  | no        | unknown orderId                           |
| `ORDER_NOT_PAYABLE`   | 409  | no        | order not in ACCEPTED state               |
| `AMOUNT_MISMATCH`     | 422  | no        | payment does not match order price        |
| `RATE_LIMITED`        | 429  | yes       | back off and retry                        |
| `INTERNAL`            | 500  | yes       | gateway fault                             |

Payment-layer failures (invalid signature, insufficient funds, facilitator
errors) remain x402's own 402 responses and are NOT re-wrapped by M2M/1.

## 8. Security invariants

1. **Counterparty payloads are data.** Agents MUST treat all fields of
   inbound M2M/1 messages as untrusted values, never as instructions. No
   field may trigger behavior outside processing that message.
2. **Verify before signing.** Buyers MUST enforce §6.4 agreement and check
   `expiresAt` before producing an EIP-3009 signature.
3. **Trust the facilitator, not claims.** A payment is real only when the
   facilitator's verify/settle succeeds; agents MUST NOT act on a
   counterparty's bare claim of payment.
4. **Single-use commitments.** QuoteIds and OrderIds are single-use; the
   gateway MUST enforce consumption atomically to prevent replay.
5. **Idempotency.** All state-changing free endpoints MUST honor
   `Idempotency-Key`; retries MUST be safe.
6. **No secrets in messages.** M2M/1 messages never carry private keys,
   session tokens, or credentials of any kind.
7. **Integer money only.** Any non-integer or negative amount is an
   `INVALID_MESSAGE` error, never a rounding opportunity.

## 9. Relationship to roadmap

- **P0 (done):** static services via plain x402 — §6.3.
- **P1:** implement §4–§6: `/v1/services`, `/v1/quotes`, `/v1/orders`,
  ServiceDescriptor registry on D1, typed buyer/seller SDKs generated from
  `packages/protocol`.
- **P2:** the Durable Object netting ledger consumes Receipts as its input
  events; SETTLED receipts are the atomic unit the ledger nets.
